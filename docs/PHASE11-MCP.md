# Phase 11 MCP transports and security

The phase and slice counts below describe their historical checkpoints. For the
current eighteen-tool registry, including later development tools, see
[V1-SPEC.md, Section 2.1](V1-SPEC.md#21-current-normative-v1-mcp-and-production-contract).
Exactly five current tools are production-eligible; that subset is unchanged.

Kodi Lab's primary MCP authority is modern Streamable HTTP POST `/mcp`, exact
protocol `2026-07-28`. Exact legacy `2025-11-25` is a bounded stateless HTTP
compatibility mode. Canonical stdio is modern-only and is not a second server
implementation.
Installed command `kodi-lab-mcp-stdio` forwards bounded stdio requests to the
same authenticated loopback HTTP route, so both transports use identical
durable client identity, credential lifecycle, preset permissions, exact target
grants, target policy, tool registry, capability/state checks, tool schemas,
ordering, and bounded error mapping.

## Generic stdio client configuration

Configure:

- command: `kodi-lab-mcp-stdio`;
- environment: `KODI_LAB_MCP_TOKEN=<token shown once by Web administration>`;
- arguments: none;
- target choice: explicit `target_id` in every target-scoped tool call.

Do not put the token in argv, a URL query, an MCP protocol payload, or a
plaintext client file generated by Kodi Lab. The adapter reads no token from
stdin. Environment variables are not perfect secret storage: sufficiently
privileged same-user or root processes may inspect them. This design addresses
the intended local/LAN trust boundary, not hostile same-account isolation, and
does not make plaintext config storage safer.

The default URL is `http://127.0.0.1:8100/mcp`. For development/test listeners,
`KODI_LAB_MCP_URL` may select another port on exact `127.0.0.1` or `localhost`,
but the scheme remains `http`, the path remains `/mcp`, and userinfo, query,
fragment, redirects, and remote hosts are rejected. The adapter is therefore
not a generic MCP forward proxy.

## Authority and lifetime

Every stdio request carries `Authorization: Bearer <token>` to `/mcp`. The
adapter does not inspect token authority, construct Kodi Lab repositories or
services, or cache a verifier, principal, grant, preset, target policy,
capability, state, or tool list. Revoke, disable, preset changes, grant removal,
and policy changes therefore apply on the next request.

There is no stdio initialize/initialized exchange or legacy fallback,
`Mcp-Session-Id`, application transport session, selected/default target, GET
stream, daemonization, or durable adapter state. Stdin EOF cancels active work
and ends the process. Input frames are bounded to 64 KiB before JSON parsing;
four workers and an eight-item backpressured queue bound local work while the
HTTP server retains authoritative admission. HTTP responses are read
incrementally to the exact 8 MiB PNG base64 maximum plus a fixed 64 KiB
JSON/metadata allowance. Stdout is serialized and awaited, so a client that
stops reading applies pipe backpressure instead of creating an unbounded output
queue.

The adapter executable alone grants no authority. A process must possess a
valid bearer, and that bearer grants only its durable MCP client's current
intersection of permission, exact grant, target policy, tool metadata, target
class, capability, and state. Stdio is a transport, not an internal,
development, or production target trust class.

Kodi Lab sends no spoofable transport-origin header. Server audit observes the
HTTP authority path and does not claim that a request came through stdio;
transport classification never changes permission in this slice. Stable
adapter errors omit bearer values, tracebacks, HTTP library detail, and endpoint
internals.

## Slice 3 observation tools

Production tools are exactly lexical `addon_list`, `remote_action`,
`screenshot_capture`, `target_list`, and `target_status`.

`addon_list` requires `target.inspect` and an exact authorized target. It reuses
the transport-neutral managed add-on inventory service, defaults to 50 records,
caps at 100, and returns only bounded semantic add-on fields. It returns no path,
install directory, repository URL, cache location, raw Kodi result or internal
database identity.

`screenshot_capture` requires `target.visual`, an exact authorized target, exact
curated screenshot capability and reconciled acceptable runtime state. It makes
at most one call to the existing durable screenshot service and returns official
MCP native `ImageContent` with `mimeType=image/png` plus compact structured
metadata. The 8 MiB validated PNG ceiling is unchanged. The same latest cache,
failed-refresh retention, one-per-instance exclusion and four-global-capture
bound apply to Web, HTTP MCP and stdio MCP.

Phase 13 Slice 3 preserves this exact schema and permission while adding a
second semantic adapter below the same authorization boundary. A verified
external-development target satisfies `screenshot` only through its configured
maximum and an independently paired, reachable, identity-pinned bridge with
verified screenshot capability. That adapter returns authenticated, strictly
validated PNG bytes without persistence or a remote path. Managed screenshot
behavior remains unchanged; bridge administration never enters MCP and the
catalog remains fifteen tools.

Built-in Add-on Development, Read-only Inspection and Full Lab Control presets
contain both `target.inspect` and `target.visual`. Phase 14 Slice 4A later
activates the non-clonable Production Remote Kodi maximum only for external
production. A client with only `target.inspect` discovers
`addon_list`, `target_list` and `target_status`; `target.visual` additionally
reveals `screenshot_capture`. Discovery does not replace invocation-time exact
grant, target policy, target-class, capability or state checks.

## Slice 4 replay-safe remote control

`remote_action` requires `target.control` and exactly `request_id` UUID,
`target_id`, and the existing closed semantic action enum. Add-on Development
and Full Lab Control contain `target.control`; Read-only Inspection does not.
Phase 14 Slice 4A activates exact Production Remote Kodi for the seven-action
production navigation subset. Discovery uses current client preset permission,
while every new non-production invocation rechecks current
credential/client state, exact grant, target policy, internal target class,
semantic-remote capability and running/ready/reconciled state.

The tool wraps the existing actor-aware `BrowserRemoteService`. Kodi mappings,
active-player choice, mutation coordination, one-dispatch/no-retry transport,
remote limiter, and navigation screenshot refresh remain service-owned. HTTP and
stdio therefore share exactly the same durable client/request namespace.

Migration `0038_mcp_remote_control` persists one receipt before dispatch, unique
by `(client_id, request_id)`. Exact completed replay returns stored semantic
output without rate consumption, Kodi dispatch, or screenshot refresh. Pending
or uncertain replay returns `remote_action_ambiguous`; a target/action mismatch
returns `request_id_conflict`. Credential rotation retains the client namespace.
Receipts survive target deletion and retain no foreign runtime or transport
detail. Coherent completed receipts expire after 30 days through opportunistic
cleanup; pending or ambiguous receipts remain protected and capacity-consuming.
The table is capped at 10,000 per client and 100,000 globally. Saturation returns
`remote_action_receipt_capacity`; clients and Web administrators cannot delete
or manually replay receipts.

Raw JSON-RPC, lifecycle, snapshots, settings mutation, library/music queries,
add-on execution, logs, diagnostics, external targets and Phase 12 workflows
remain excluded.

The applicable official runner subsets remain `tools-list`,
`dns-rebinding-protection`, and `http-header-validation`. Its canned
`tools-call-image` scenario requires a diagnostic fixture named
`test_image_content`, which is intentionally not added to the closed production
catalog. Native image behavior is instead exercised through the pinned official
SDK over both direct HTTP and the canonical stdio subprocess, including exact
MIME, PNG signature, decoded dimensions, byte bound and structured metadata.

## Slice 5 custom presets

Web administration can clone Add-on Development, Read-only Inspection, or Full
Lab Control into a custom preset. The administrator supplies only a 1–120
character trimmed unique display name and the built-in UUID. Kodi Lab creates a
new UUID and copies the built-in's current server-known permissions. Production
Remote Kodi cannot be cloned. Phase 14 Slice 4A later makes that exact built-in
assignable only for external-production targets.

The permission snapshot is immutable: there is no per-permission editor,
rename, deletion, conversion, or custom-from-custom clone. A later permission
added to a built-in does not appear in an older custom preset. Custom presets
use the same client and internal-target policy assignment paths. Reassignment
takes effect on the next request without transport restart and never falls back
to broader authority. Creation, assignment, and displaced-preset unassignment
events contain only bounded UUIDs/event kinds; no token or form payload is
recorded. Existing schema suffices, so Alembic remains
`0038_mcp_remote_control`.

## Slice 5 legacy HTTP compatibility

Exact `2025-11-25` uses the same POST `/mcp` SDK application with
`stateless_http=True`. Its first headerless request must be a valid initialize
request explicitly offering `2025-11-25`; all later requests carry exact
`MCP-Protocol-Version: 2025-11-25`. Explicit modern and legacy method sets are
disjoint. Unsupported or malformed traffic is rejected and never retried in
the other era. `Mcp-Session-Id` is rejected and never emitted or persisted.

Every HTTP request uses the same `Authorization: Bearer` verifier, peer-keyed
authentication-failure limiter, client-keyed admission, concurrency caps,
principal, discovery filter, exact grants, target policy, target class,
capability/state checks, tool schemas/adapters, replay receipts, audit fields,
and privacy errors. No query key, cookie, alternate credential store, selected
target, or protocol-specific privilege exists. Modern remains the documented
default. Legacy support may be removed only by an explicit future decision with
compatibility evidence and schema/version policy review.

Legacy stdio is not supported. The current proxy is intentionally stateless and
modern; handshake-era stdio would require negotiation state. Older clients can
use legacy HTTP without creating a second stdio server or application authority.

## Phase 14 Slice 4A production replay addendum

Production reuses the same `(client_id, request_id)` base receipt and all
transports share it. A one-to-one immutable binding records native generation,
bridge revision, policy/epoch, inspect/navigate scopes, exact presets, grant and
applicable native-HTTP acknowledgement before dispatch. Terminal replay is
historical retrieval for the same authenticated enabled client and does not
require current scope, generation, bridge reachability or clear mutation veto.
Pending/ambiguous or incoherent production receipts never redispatch and are
protected from retention cleanup. Only a coherent completed base receipt,
production binding and matching terminal audit expire atomically after the
ordinary 30-day retention window. Action-aware policy permits only seven
standing navigation values; future transient and prohibited values never reach
adapter dispatch.

## Phase 14 Slice 4B production approval replay addendum

For the seven transient production actions, a new exact client/request creates
only an approval intent and requested transition. No Phase 11 receipt exists
until Web approval is consumed. Exact duplicates return the same pending or
terminal approval; changed target/action/digest conflicts.

Consumption and receipt claim are one transaction: approval becomes consumed
while the base pending receipt, transient production binding, semantic audit,
consumed event and durable admission state are committed. After that commit the
base receipt is authoritative across modern HTTP, stdio and compatibility HTTP.
Pending or ambiguous replay never dispatches; coherent completion replays its
historical result. A crash after commit but before native send therefore may
lose the approved action but cannot cause a duplicate. Approval retention keeps
all live, pending, ambiguous, missing, mismatched or malformed relationships
protected; only coherent old terminal bundles expire atomically.
