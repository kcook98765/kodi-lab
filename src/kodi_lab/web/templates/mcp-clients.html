Agents

Connect one MCP-compatible agent to Kodi in five steps. A client holds that agent's permissions and tokens, separate from your Web administrator account.

1. Create or select a client and choose permissions

Use a separate client for each agent. If you already have one, open it in Your clients below.

Production Inspection is for read-only health, add-on and UI-state inspection. Choose Production Visual Inspection if you also need screenshots. Neither preset grants Kodi control or development access.

2. Allow access to your Kodi

Open your client in Your clients. Under Kodi access, select Grant for your Home Kodi, then Grant current inspect scope. For screenshots, also grant the current visual scope when available. These are explicit actions; creating a client does not grant access.

3. Issue a token and copy configuration

In your client, choose a Token lifetime and select Issue token. The configuration below will include the new token. Copy and store it securely before leaving or reloading this page: the token is shown only once and cannot be recovered.

Connection method

Trusted LAN HTTP is unencrypted. Bearer tokens and MCP traffic can be intercepted, read or modified on the network. An intercepted token can be replayed with that client's permissions and target grants. Use this only on a private LAN you trust; prefer short-lived, least-privilege tokens. HTTPS protects traffic in transit.

Administrator connection setup

Keep Web administration on its existing local address. Configure a separate MCP-only listener for the chosen private interface and allowed subnet. HTTPS requires a matching certificate trusted by each agent. Trusted LAN HTTP requires explicit enablement and sends credentials and traffic unencrypted; it can coexist with HTTPS. The administrator setup guide is docs/NATIVE-LAN-MCP.md in the Kodi Lab package or checkout. Settings alone do not start a listener or grant access.

For an agent on another authorized LAN computer, use this HTTPS URL with Streamable HTTP. No local Kodi Lab adapter or SSH forwarding is needed. Send Authorization: Bearer with your token on every MCP request. Web login cookies do not authenticate agents.

Your agent must trust the certificate for this exact address. For a private certificate authority, have your administrator install its CA certificate in the agent's trust store. Keep TLS verification enabled. The server's connection check cannot verify connectivity or certificate trust on your agent's computer.

HTTP supports MCP 2026-07-28 and 2025-11-25. Older revisions, including 2025-06-18, are rejected. Choose a client that supports one of these versions and custom bearer headers.

Use this explicitly enabled HTTP endpoint on the trusted LAN with Streamable HTTP. No certificate setup, adapter installation or SSH forwarding is required. The connection is unencrypted; the server's reachability check does not authenticate the remote server or make the network safe.

Send the token only in Authorization: Bearer. MCP 2026-07-28 and 2025-11-25 use the same permissions, target grants, expiry and revocation checks as HTTPS. Web cookies do not authenticate agents.

The kodi-lab-mcp-stdio command must be installed where your agent runs. It connects to a local 127.0.0.1 address on that computer and supports MCP 2026-07-28.

Agent on another computer or command unavailable?

Install the Kodi Lab package in the agent's environment so kodi-lab-mcp-stdio is on its command path, or use the full path to that installed command in the configuration. With stdio, an agent on another computer needs an existing local forwarding arrangement to Kodi Lab. A LAN Web address is not supported by this command; choose LAN HTTPS or deliberately select Trusted LAN HTTP above when available.

This server's configured port is {{ agent_stdio_port | default(8100) }}. Use the port reachable on the agent's computer: normally 18100 for the Docker host publication, or your local forwarding port. The configured server port does not verify access from your agent.

You can also select and copy the configuration manually. Protect settings containing your token as you would a password. Keep HTTP tokens in authorization headers and stdio tokens in env; never put tokens in URLs, command arguments or shared project files.

4. Add configuration to your agent

Open your agent's MCP server settings and add the configuration for your selected connection method. The HTTP example uses type: http, url and headers, as in Claude Code or VS Code. The stdio example uses command, args and env. Your agent may require a server name or an outer configuration wrapper; follow its own instructions. Save in protected user settings, then reconnect or restart the agent.

5. Verify read-only access

Ask your agent: List the Kodi instances I can access, then inspect the health of my Kodi. It can use target_list, then target_status with that Kodi's target_id. Both Home inspection presets also support addon_list and inspect_ui_state; screenshots require Production Visual Inspection and the visual scope.

If connection fails, check the selected transport, supported MCP version and token expiry. For either LAN method, check endpoint and network access; HTTPS also requires certificate trust. For stdio, check the installed command and local port. If access is denied, check the client preset, Kodi policy and current scopes in your client's Kodi access section. A token alone does not authorize a Kodi.

Creating a client or issuing a token does not grant access to Kodi. The client preset and the Kodi policy must both allow the requested inspection.

If the required control is missing, review this client's preset and the Kodi policy under Advanced administration.
